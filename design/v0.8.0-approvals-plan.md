# PixelCI v0.8.0: transition-keyed approvals, merge-base baselines

## 0. Design summary

1. **Decisions are stored as transitions.** A new table `screen_decisions` holds one row per approved or rejected change: screen, **from** image (or absent), **to** image (or absent), kind, who decided, where, and when.
    - An image is identified by its **image source**: the build whose upload holds the pixels (`matchedBuildId ?? buildId`), plus a sha256 of the PNG bytes.
2. **A screen is auto-approved only if three things hold:**
    - Its baseline's image source equals the decision's `from`, by source id or, failing that, by content hash.
    - The decision is newer than that baseline image (the "epoch" rule below).
    - Its upload matches the decision's `to`: hash first, then `screensMatch` with the screen's current tolerances and masks.
    - If several decisions match, the newest one wins. A rejection that is newer than every matching approval blocks.
3. **Epoch rule.** A decision applies only if `decision.id > epoch`. Both are uuid7 values, so this is a time comparison.
    - When the baseline is present, the epoch is the id of the baseline's image source row.
    - When the baseline is absent, the epoch is the id of the latest accepted default-branch tombstone for that screen at or before the reference build (zero if there is none).
    - This is what fixes the re-added-screen case (#7) and the revert-then-reintroduce case, which pure transition matching would otherwise wave through.
    - Source-id matches always pass the epoch rule by construction. It only ever rejects hash-equal re-uploads and absent baselines.
4. **The reference is the accepted default-branch build at the merge base.**
    - The CLI sends up to 50 first-parent ancestors of the merge base, nearest first.
    - The server picks the first ancestor whose default-branch build is accepted (`changes approved` or `no changes`).
    - If none qualifies, it falls back to the latest accepted build and records `referenceSource='latest'`; the UI warns.
    - The chosen reference is **stored on the build** (`referenceBuildId`). The UI, the tolerance preview and the approve endpoint all reuse it instead of recomputing.
5. **The previous-same-branch path and app-wide carry-forward are deleted.**
    - Branch approvals are ordinary decisions, so rebases (#5) are handled by the from-match.
    - In-progress review marks carry forward only from the immediately preceding build on the same branch, and only for the same transition. They carry a provenance pointer and no reviewer.
6. **Revocation** sets `revokedAt` on a decision. It affects future processing only.
7. **The diff always matches the images shown.**
    - Processing stores the authoritative diff at the build screen's own path, against its own baseline's image source.
    - The UI and the external read API take the diff and the "new" image from the row's own build for every changed row. They no longer follow `matchedBuildId`.
    - Only `no changes` rows become `pendingDeletion`.
8. **No decisions are backfilled ("start fresh"); this is flagged as a product call in §10.** Existing approved builds keep working as baselines. Legacy builds get `referenceBuildId` backfilled with `referenceSource='legacy'`.
9. **Cost is bounded per screen:**
    - At most 1 baseline comparison, skipped when the hashes are equal.
    - 1 decision query, capped at 20 rows.
    - At most 4 speculative pixel comparisons.
    - At most 1 carry-forward comparison.
    - 1 absent-epoch query, for new screens only.

### 1.5 Historical approvals: start fresh (recommended)

- Legacy approvals were made against the baselines this release declares wrong:
    - latest-main instead of the merge base (#4);
    - the previous-branch-build path (#5);
    - loose cross-branch matching (#2).
- Converting them to transitions would import exactly the false approvals being fixed. Under the stale-branch pattern, for example, a `C→A` approval would be backfilled.
- The cost of starting fresh is one re-review per in-flight branch, on its next build or on its merge. Nobody external runs PixelCI, so this lands only on your instance.
- Baselines are unaffected: they are builds, not decisions.
- Legacy builds still in `needs review` at upgrade create decisions when approved. They use the backfilled reference and are `branchScoped` (see §3.1).

### 2.1 Reference resolution (`Reference.ts`)

```ts
export const ACCEPTED: BuildEntity['status'][] = ['changes approved', 'no changes'];
// 'no changes' builds are complete (every screen 'no changes', no tombstones), so their rows (matched) form a full baseline.

async function resolveReference(app, build): Promise<{ build?: BuildEntity; source: 'ancestor' | 'latest' | 'none' }> {
    if (!app.defaultBranchId) return { source: 'none' };
    if (build.baseCommits?.length) {
        const hits = await BuildEntity.query()
            .filter({
                appId,
                branchId: app.defaultBranchId,
                commitHash: { $in: build.baseCommits },
                status: { $in: ACCEPTED },
                id: { $ne: build.id }
            })
            .find();
        const byHash = keyBy(hits, 'commitHash');
        for (const sha of build.baseCommits) if (byHash[sha]) return { build: byHash[sha], source: 'ancestor' };
    }
    const latest = await BuildEntity.query()
        .filter({ appId, branchId: app.defaultBranchId, status: { $in: ACCEPTED }, id: { $lt: build.id } })
        .orderBy('id', 'desc')
        .findOneOrUndefined();
    return latest ? { build: latest, source: 'latest' } : { source: 'none' };
}

/** For display/compare/approve: stored reference when set; legacy computation only when referenceSource is null (0.7 pod). */
async function referenceForBuild(app, build): Promise<BuildEntity | undefined>; // replaces BuildScreens.controller.ts:137-143

/** Map<screenId, { refRow, sourceBuildId, sourceRowId, hash }> — 2 queries: ref rows (isRemoved=false), then source rows
 *  (screenId IN refScreenIds AND buildId IN distinct sourceBuildIds), keyed `${buildId}:${screenId}`. */
async function loadBaselines(appId, refBuildId);
```

- Default-branch builds: the CLI sends `rev-list --first-parent HEAD`. The build's own entry is excluded by `id != build.id`, which gives "first-parent parent".
- Because ancestry decides, not recency, an old commit processed late still compares against its own ancestor.

### 2.3 `findDecision` (`Decisions.ts`)

```ts
const MAX_DECISION_CANDIDATES = 20,
    MAX_DECISION_PIXEL_COMPARES = 4;
candidates = ScreenDecisionEntity.query()
    .filter({
        appId,
        screenId,
        revokedAt: null,
        id: { $gt: epoch },
        ...(from ? { $or: [{ fromImageBuildId: from.buildId }, ...(from.hash ? [{ fromHash: from.hash }] : [])] } : { fromImageBuildId: null }),
        toImageBuildId: to ? { $ne: null } : null,
        $or2: [{ branchScoped: false }, { branchId }] // express as nested $and/$or in TSF syntax
    })
    .orderBy('id', 'desc')
    .limit(MAX_DECISION_CANDIDATES)
    .find();
return pickDecision(candidates, to ? { hash: to.contentHash } : 'absent', toImageBuildId => screensMatchSafe(toImageBuildId, row));
```

`pickDecision` is pure and unit-tested. The newest match wins, under a budget:

```ts
async function pickDecision(cands, upload, match, budget = MAX_DECISION_PIXEL_COMPARES) {
    const unknownKinds = new Set<Kind>();
    const cache = new Map<string, boolean>();
    for (const c of cands) {
        // newest first
        let m: boolean | undefined;
        if (upload === 'absent') m = c.toImageBuildId === null;
        else if (!c.toImageBuildId) m = false;
        else if (upload.hash && c.toHash === upload.hash) m = true;
        else if (cache.has(c.toImageBuildId)) m = cache.get(c.toImageBuildId);
        else if (budget > 0) {
            budget--;
            m = await match(c.toImageBuildId);
            cache.set(c.toImageBuildId, m);
        }
        if (m === undefined) {
            unknownKinds.add(c.kind);
            continue;
        }
        if (!m) continue;
        return [...unknownKinds].some(k => k !== c.kind) ? undefined : c; // a newer unchecked candidate of the other kind could win
    }
    return undefined;
}
```

- `screensMatchSafe` catches S3 errors, logs them, and returns false. This mirrors the existing catch at L316-331.
- The from side uses no fuzzy matching. Images judged equal are canonicalized through `matchedBuildId`, so equivalent baselines share a source id. Fuzzy from-matching would be unbounded and would weaken the guarantee.

### 2.4 Case coverage

| Case                          | Behaviour                                                                                                                                                                         |
| ----------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| First build ever              | No reference, so every screen is absent with epoch 0. Approving records `∅→img` decisions, which later match on main or other branches.                                           |
| Default-branch build          | Reference is the nearest accepted first-parent ancestor. Main's decisions apply app-wide.                                                                                         |
| New screen                    | Absent baseline, absent epoch. Auto-approved by any newer `∅→X` with `X ≈ upload`.                                                                                                |
| Removed screen                | Tombstone: from = baseline source, to = null. Approved removals become `X→∅` decisions. Removals can't be rejected one by one (unchanged rule, `BuildScreens.controller.ts:437`). |
| Re-added screen               | Absent epoch is the latest main tombstone, so `∅→X` decisions older than the removal don't apply (#7).                                                                            |
| Revert then reintroduce       | The new baseline source after a revert is newer than the old `A→B` decision. A hash match on `from` fails the epoch rule, so it needs review.                                     |
| Size change                   | from-identity is unaffected. The to-match pads (existing behaviour).                                                                                                              |
| `canvasTooLarge`              | `performDiff` stores the red-tint diff. The to-match pixel compare fails, but a **hash-equal** approved image still auto-approves, which was impossible before.                   |
| Fallback reference (`latest`) | Works as before, but approvals from non-default-branch builds are `branchScoped` (see §3.1).                                                                                      |
| Legacy rows (no hash)         | Hash fast paths are skipped. Pixel compares run, and lazy hashing fills the hashes in.                                                                                            |

### 2.5 `RemovedScreens.ts`

Rewrite `computeRemovals` to take:

- the baseline map;
- the uploaded screen ids;
- a `findRemovalDecision(screenId, B)` callback (to = null, epoch = `B.sourceRowId`).

Then:

- Each tombstone gets `baseImageBuildId = B.sourceBuildId`.
- If an approved decision matches, it also gets `status='changes approved'`, `decisionId` and `approvalBuildId = d.buildId`; otherwise `needs review`.
- Delete the previous-tombstone branch (`RemovedScreens.ts:28-50`).

### 2.6 Carry-forward of review marks (branch-local, bounded)

Replaces L290-346.

- `prev` is the latest build on the same branch with `id < current`, excluding draft/processing/canceled/failed (1 query).
- Proceed only if `prev.status ∈ {needs review, changes rejected}`.
- Load `prev`'s rows that have `reviewStatus != null` (1 query).
- For each upload with status `new` or `needs review` and no `reviewStatus` yet:
    - require `p.baseImageBuildId === row.baseImageBuildId`. For legacy `prev` rows where this is null, skip; legacy marks don't carry.
    - require the to side to match: hash equal, else one `screensMatchSafe`.
    - If both hold, copy `reviewStatus` and `reviewComment`, and set `reviewCarriedFromId = p.reviewCarriedFromId ?? p.id`.
    - Leave `reviewedById` and `reviewedAt` **null**. This fixes the audit misattribution in #6.

### 2.7 Concurrency

- Processing only reads decisions. The approve endpoint writes them inside the transaction that locks the build row.
- A build processed while another is being approved may miss that decision. The result is conservative (`needs review`), and a re-push picks it up.
- The unique `buildScreenId` index, together with the status check under lock (`Builds.controller.ts:655-656`), makes double approval impossible.
- Revocation takes effect for processing that starts after its commit.
- Retries after a lost lease recompute from scratch, because rows are reloaded and nothing is written before the fenced transaction. Diff objects are overwritten at the same path.
- Clock skew: epoch comparisons use uuid7 timestamps minted on different pods. Uploads and decisions are separated by human review time, so millisecond skew doesn't matter.

### 2.8 Cost per build (N uploads, C changed, R removals)

- **Queries:** about 7 fixed, plus C decision queries, plus one absent-epoch query per new screen, plus R decision queries.
- **Pixel comparisons:**
    - at most N baseline compares, 0 when hashes are equal;
    - at most 4C speculative compares;
    - at most 1 carry-forward compare per changed screen.
- v0.7 was unbounded: every explicit approval of the screen, plus every reviewed row since the lower bound, each pixel-compared.
- Expected net effect: faster. Most unchanged screens are byte-identical, so they skip S3 and pixelmatch.

## 3. Approve, reject, revoke

### 3.1 `Builds.controller.ts` `approve` (L643-719)

Inside the locked transaction:

1. Fill reviewer fields, as at L668-673: for each changed row (`new` / `needs review`, tombstones included) with no review **or** with a carried or decision pre-mark and `reviewedById == null`, set `reviewStatus ??= 'approved'`, `reviewedById = user.id`, `reviewedAt = now`. The submitter has accepted it.
2. Resolve `from`:
    - if `build.referenceSource ∈ {ancestor, latest, none}`: use `row.baseImageBuildId`;
    - otherwise derive it from `referenceForBuild` rows (legacy builds).
    - Batch-load the source rows to get `fromHash`.
3. **If any row is rejected:** insert `kind='rejected'` decisions for rejected non-tombstone rows only, and set `row.decisionId`. The build becomes `changes rejected`. Approved marks in a rejected build do not become decisions (product call 5).
4. **Otherwise:** insert `kind='approved'` decisions for every changed row (tombstones too), with:
    - `to = row.isRemoved ? null : { buildId: row.buildId, hash: row.contentHash }`
    - `branchScoped = build.branchId !== app.defaultBranchId && build.referenceSource !== 'ancestor' && build.referenceSource !== 'none'`
    - `decidedById = row.reviewedById`, `comment = row.reviewComment`
    - Set `row.decisionId` and `status = 'changes approved'`. Leave `approvalBuildId` null, since the approval was explicit.

- A shared `recordDecisions(txn, ...)` lives in `Decisions.ts`.

### 3.2 New `controllers/Decisions.controller.ts`

- Route: `POST /api/apps/:appId/decisions/:id/revoke`, with `UserAuthMiddleware` and `assertCanReviewAppId`.
- Conditional patch `WHERE id AND appId AND revokedAt IS NULL`. It is idempotent: already revoked returns 200 with the current state.

```ts
export async function resolveBase(o: { defaultBranch; branchName; commitHash; env; git; log }): Promise<IBase | undefined>
  // never throws: any failure → log.warn(...) and return undefined
  if env.PIXELCI_BASE_COMMIT → basePoint=it, source 'override'
  require `git --version` and `rev-parse --is-inside-work-tree`, else warn "no git history: comparing against the latest approved <default> build"
  target = commitHash if `cat-file -e <commitHash>^{commit}` else HEAD
  if branchName === defaultBranch → basePoint = target, source 'first-parent'
  else if GitLab merged_result (CI_MERGE_REQUEST_EVENT_TYPE ∈ {merged_result, merge_train}) && CI_MERGE_REQUEST_TARGET_BRANCH_SHA → 'merge-request-target'
  else if GitHub GITHUB_EVENT_NAME==='pull_request' && parents(target).length===2 → parents[0], 'pull-request-base'   // `git cat-file -p` works in depth-1 clones
  else if CI_MERGE_REQUEST_DIFF_BASE_SHA → 'merge-request-diff-base'
  else if GitHub PR (head checked out) → merge-base with event pull_request.base.sha (GITHUB_EVENT_PATH)
  else: fetch default → refs/remotes/pixelci-base/<default> (`--no-tags`, `--depth=50` if shallow) unless PIXELCI_GIT_FETCH=false;
        mb = merge-base target refs/remotes/pixelci-base/<default>;
        if fail && `rev-parse --is-shallow-repository` = true: for d of [200, 1000]: `fetch --no-tags --deepen=d origin <target> +refs/heads/<default>:refs/remotes/pixelci-base/<default>`; retry
        source 'merge-base'
  commits = `rev-list --first-parent --max-count=50 basePoint`; on failure: try `fetch --no-tags --depth=50 origin <basePoint>` then retry; else [basePoint]
  return { commits (validated lowercase hex, deduped), source }
```

## 10. Risks, product calls, cuts

### Product calls (recommended default first)

1. **A rejection followed by an approval elsewhere.** Default: the newest decision wins globally, so `reject2`'s R2 passes. The reviewer who approved saw the pre-marked rejection and who made it. Alternative: rejections stick on their own branch until re-approved there. That is roughly 15 lines in `pickDecision`: prefer branch-local decisions first.
2. **Historical approvals.** Default: start fresh (§1.5). Alternative: backfill the last 14 days as `branchScoped` decisions.
3. **Revocation.** Default: future builds only. Re-evaluating would flip CI checks that already passed and can't be un-reported.
4. **Approvals made against a fallback baseline** (no merge base, non-default branch). Default: reusable only on the same branch, which contains the regression risk from #4.
5. **Per-screen approvals inside a rejected build.** Default: they stay branch-local marks, not global approvals, matching today's "nothing promoted".

### Risks

- **CI git environment:** shallow clones, missing credentials, `safe.directory`, slow fetches on huge repos. Mitigations: bounded deepen, timeouts, never failing the job, a visible fallback, and docs. Dogfood sets `GIT_DEPTH: 0`; real-git tests cover the deepen path.
- **Rolling deploy:** builds processed by a v0.7 pod have `referenceSource` null and are handled by the legacy path. Approvals made through a v0.7 pod create no decisions. Rollback stays safe because every change is additive and `approvalBuildId` keeps v0.7 semantics.
- **Conservative re-asks:** the epoch rule, the from-match by identity or hash only, and the candidate and budget caps can all produce `needs review` where v0.7 auto-approved. Log every cap hit.
- **Base commit not yet approved:** when a PR or branch's base commit build is still running or unapproved, the nearest approved ancestor is used, and main's pending change appears on the branch (documented).
- **Non-deterministic PNG encoders** lose the hash fast paths. Correctness is unaffected.
- **GitLab MR pipelines** already create a pseudo-branch `refs/merge-requests/N/head` (existing behaviour, `VcsGitLab.service.ts:99`). Base detection works there, but builds don't land on the source branch. Not fixed in v0.8.0.
- **Future storage cleaner:** it must never delete a `matchedBuildId` target or a decision's from/to image. Note this at `ProcessBuild` where `pendingDeletion` is set.
- **Response canary** fails on any unlisted route. Step 3 must add the revoke case.
